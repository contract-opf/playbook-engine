# Pinned docling / OCR stack for the Docker runtime (issue #244).
#
# Bumped to docling 2.140.0 for issue #252: 2.113.0 silently ignored
# `--ocr-lang eng` and ran the Chinese recognizer (garbled or timed-out scans);
# 2.140.0 honours the BCP-47 form (`iso:en`) and the explicit OCR engine
# (`--ocr-engine tesseract`) that playbook_engine/extraction.py now passes.
#
# Why this exists: the Dockerfile used to install `docling` unpinned. A newer
# docling release changed its automatic OCR engine selection so that our
# `--ocr-lang eng` was rejected (no installed engine served `eng`), docling
# failed, and extraction silently fell back to the legacy reader. The weekly
# Docker Smoke Test caught it. These pins are the exact set in the image built
# from the last known-good commit, so a docling release can never degrade
# extraction without a deliberate change here.
#
# How to bump deliberately:
#   1. Edit the pins below (move docling and its sibling packages together).
#   2. `make docker-build`, then run the smoke test
#      (`gh workflow run docker-smoke.yml --ref <branch>`, or the steps in
#      .github/workflows/docker-smoke.yml locally). It must report
#      `extractor=docling`, not `legacy`.
#   3. Only then merge. A bump that needs the new OCR API (`iso:` language
#      codes, explicit engine selection) also needs the matching extraction.py
#      change in the same commit.
#
# torch/torchvision come from the CPU-only index (see the Dockerfile); the pin
# is the public version, which matches the `+cpu` local build.

docling-slim==2.140.0
